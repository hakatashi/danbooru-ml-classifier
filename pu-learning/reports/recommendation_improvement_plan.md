## 0. エグゼクティブサマリ

- **補足1の仮説（お気に入りを含むページ = 閲覧済みとみなす）は有効**。実データで再構成した結果、**25,850 件の擬似インプレッション（正例 1,740 / 負例 24,110、正例率 6.7%）** が今日時点で取り出せる。
- この負例は「現行モデルがトップに押し上げたが選ばれなかった画像」= **hard negative** であり、ランキング上位の精度を直接改善する最も価値の高い信号。
- ただし **13% のお気に入りは 10 ページ目以降**（favorite までの日数中央値 7 日）にあり、Gemini タブの通常閲覧では説明できない。ページ単位の信頼度重み付けが必要。
- **学習なしで即座に得られる改善がある**: 既存モデルの rank-average アンサンブルで、実運用域（ページ0-1）のページ内 AUC が Gemini 0.656 → 0.66〜0.69 台に向上（後述 1.5、深度帯別）。ただし当初報告した「0.609→0.703」は深いページの寄与を均して過大評価していた数値であり、**実運用域（p0-1）ではこの改善幅は出ない**。深度帯によって最良のアンサンブル構成が異なる（後述）。
- **[訂正] Recall@50 を Gemini との比較指標に使ってはいけない**。お気に入りラベル自体が Gemini を見て付けられたものなので、Gemini の Recall@50 は構造的に高くなる（循環参照）。追加検証では直近30日のお気に入り226件のうち85.8%がGemini top-50内、97.3%がtop-500内だった。主指標は**ページ内AUC**（同一ページ内でのみ正例/負例を比較する層別比較）とし、Recall@50はGemini自身の順位付けバイアスを常に付記した参考値として扱う。
- 中長期の本命は **(a) 実測インプレッションログ**、**(b) 特徴量ストア**、**(c) 2 段ランキング（recall 用 PU モデル + precision 用 re-ranker）** の 3 点。追加検証で、インプレッションで学習した単純なロジスティック回帰を全画像に直接適用すると Recall@50 が 0.000 まで崩壊する一方、Gemini top-500 の再ランクに限定するとページ内AUCで Gemini を上回ることを確認した。**学習型 re-ranker は必ず 2 段構成（stage-1 で候補生成 → stage-2 で再ランク）にする必要がある**——これは提案ではなく実測上の必須条件。

### 1.5.1 【訂正】ページ深度別に見ると、上記の改善幅は実運用域では出ない

|---|---:|---:|---:|---:|---:|
| Gemini（現行） | 0.656 | 0.630 | 0.506 | 0.535 | 0.608 |
| rank-average private系9モデル（Virgo案） | **0.693** | **0.683** | 0.663 | 0.553 | 0.666 |
| rank-average 上位5モデル（Libra案） | 0.676 | 0.668 | **0.725** | **0.705** | 0.677 |
| `pixai_pixiv_private_elkan_noto`単体 | 0.713 | 0.700 | 0.693 | 0.565 | 0.684 |

（p0-1: 165ページ、p0-4: 247ページ、p5-19: 114ページ、p20+: 156ページ、全108日ベース）

**読み方**:

- **実際に日々目にする p0-1 では、改善幅は 0.656→0.69 台にとどまる**（1.5 で報告した 0.609→0.703 ではない）。1.5 の数値は p20+ の深いページ（本来ほぼ閲覧されていない可能性が高い、1.3参照）を含めて平均したことで嵩上げされていた。
- **深度帯によって最良のアンサンブル構成が異なる**。p0-1では private系9モデル平均が僅差で最良、p5-19以降では上位5モデル平均（Twitterモデルを含む）が明確に強い。単一のアンサンブルに決め打ちせず、両方を出して比較すべき。
- `pixiv_public` 系はほぼ無情報〜逆相関。**「private ブックマーク」が嗜好の代理指標として正しい**ことが裏付けられた。

### 1.5.2 【追加検証】Recall@50 は Gemini との比較に使えない（循環参照）

直近30日をテスト期間として、その期間のお気に入り226件が Gemini のランキング上でどこに位置していたかを確認した:

```
Gemini top-50  に入っていた favorite: 194/226 (85.8%)
Gemini top-500 に入っていた favorite: 220/226 (97.3%)
```

お気に入りは「Gemini タブを見て」付けられているため、Gemini の Recall@50 は構造的にほぼ満点になる。**Recall@50 を主指標にして他モデルと比較すると、Gemini が常に不当に有利になる**。実際、rank-average アンサンブル（Virgo/Libra案）はいずれも Gemini より Recall@50 で大きく劣る（0.65〜0.67 vs Gemini 0.846）——これは精度が低いのではなく、ラベル自体がGeminiの出力に依存しているため。

→ **評価の主指標はページ内AUCとする**。Recall@50はあくまで「Geminiとの一致度」を示す参考値であり、Gemini自身を基準にした自己言及的な指標であることを常に明記する。実測インプレッションログ（3.1）が閲覧経路に依存しない形で貯まれば、この問題は緩和される。

### 1.5.3 【追加検証】学習型モデルは2段構成が必須

インプレッション23,550件（訓練期間78日分）でロジスティック回帰を学習し、テスト期間の**全画像**に直接適用したところ Recall@50 = 0.000 という壊滅的な結果になった。同じモデルを「Geminiのtop-500に絞ってから再ランクする」用途に限定すると Recall@50 = 0.538、ページ内AUC = 0.741 で Gemini（0.735）をわずかに上回った。

原因は、正例1,740件に対して36次元の特徴量では、母集団全体（1日あたり数千〜1万枚）に対する汎化が効かず、Gemini自体が形成した分布の外側で暴走するため。**学習型 re-ranker（Phase B）は必ず「stage-1: 既存モデルやアンサンブルで候補を数百件に絞る」→「stage-2: その候補内だけを再ランクする」という2段構成にすること**。全画像に直接適用する設計は採用しない。

### 1.6 学習データとしての即応性

| 項目 | 値 |
|---|---|
| 閲覧済み 25,850 件のうち特徴量抽出済み | 3,046（11.8%） |
| うち正例で抽出済み | 80 / 1,740（4.6%） |

**`sankaku` は既存 manifest の走査対象外**（`extract_features.py` は `danbooru`/`gelbooru`/`pixiv` のみ）。閲覧画像の 23% が sankaku であり、**学習データに一切含まれていない**。

→ 追加抽出が必要なのは 22,804 件。ファイルは全て手元にあるので、GPU で数時間の一度きりの作業。

## 2. 補足1への回答

**結論: やるべき。ただし「閲覧済み」の定義を 3 段階の信頼度で扱うこと。**

### 2.1 なぜ効くか

現行の PU Learning は「pixiv private ブックマーク = 正例」「DMC 画像全体 = unlabeled」で学習している。unlabeled のほとんどは**モデルが既に低スコアを付けられる簡単な負例**であり、学習の後半では情報を持たない。

一方、今回の負例は **モデル自身がトップ 50 に押し上げたのに選ばれなかった画像**。これは決定境界のすぐ内側にあるサンプルで、ランキング上位の precision を直接押し上げる。しかもラベルノイズが構造的に少ない（実際に目で見て判断している）。

さらに、正例の性質が変わることも重要:

- 既存の正例 = **pixiv の過去のブックマーク**（過去の自分の嗜好、pixiv というプラットフォームの偏り込み）
- 新しい正例 = **DMC のリコメンド画面で今の自分が選んだもの**（sankaku/gelbooru/danbooru を含む、現在の嗜好、推論時と同じ分布）

**train/serve の分布が一致する**という点だけでも大きい。

### 2.2 リスクと対策

| # | リスク | 対策 |
|---|---|---|
| R1 | 深いページ（isolated deep page）は実際には閲覧していない → 偽陰性 | ページ index とラグに応じた**信頼度重み**。下記 2.3 |
| R2 | 「見たが登録しなかった」≠「嫌い」。同一作品の別ページ、既存コレクションと重複、その日の気分 | 同一 `artworkId` を負例から除外（実測 901 件）。Qdrant で cosine > 0.95 の近重複も除外 |
| R3 | **フィードバックループ**。Gemini がトップに出したものだけを学習 → Gemini のバイアスを増幅し、探索が死ぬ | (a) ランダム unlabeled 負例を一定割合ブレンド、(b) 毎日 1 ページ目にランダム枠（ε-greedy）を数枚混ぜて不偏データを積む、(c) 既存 PU 正例を prior として残す |
| R4 | 正例 1,740 件は少ない → 高次元特徴で過学習 | 生の 13,461 次元で学習しない。**既存モデルスコアのスタッキング**（30次元）+ Qdrant kNN 特徴（数次元）を主軸にする |
| R5 | 嗜好のドリフト（4月と8月で違う） | 時系列 split で評価。学習時に `favoritedAt` の新しさで重み付け（half-life 90日など） |
| R6 | 日ごとの母集団サイズ差（1,895〜10,205 枚）でページ位置の意味が変わる | ページ index ではなく **rank の percentile** で正規化した特徴も併用 |

### 2.3 ラベル生成ルール（提案）

各 `(date, page)` に**インプレッション信頼度 `w ∈ [0,1]`** を与える:

```
conf(date, page):
  favs_pages = そのdateでお気に入りが存在するページ集合
  P_max_contig = 0 から連続してお気に入りが存在する最大ページ
  if page <= P_max_contig:            w = 1.0    # 確実に順に見ている
  elif page <= 4:                     w = 0.9    # 浅いページは見ている蓋然性が高い
  elif そのページのfav数 >= 2:         w = 0.7    # 複数登録＝実際に見た証拠
  elif lag(favoritedAt - date) <= 3日: w = 0.5    # Daily 由来の可能性
  else:                               w = 0.15   # /archives 等から拾った可能性大
```

正例は `w` に関わらず重み 1.0（お気に入り登録は確定事実）。負例のみ `w` をサンプル重みに使う。

さらに負例から除外:

- お気に入り画像と同一 `artworkId`（実測 901 件）
- お気に入り画像と Qdrant eva02 cosine > 0.95（近重複）
- `status != inferred`

**この重み付けルール自体をハイパーパラメータとして検証すること**（`w` を全部 1.0 にした版との比較を評価プロトコルで行う）。実測ベースのインプレッションログが貯まれば、この推定は不要になる（→ 3.1）。

## 3. データ基盤の整備（MongoDB / Qdrant）

### 3.1 【最優先】実測インプレッションログ

**今回のページ再構成は「過去分の救済策」であって、恒久的な仕組みにすべきではない。** 今後は実際に表示された画像を記録する。

**フロントエンド** (`public/src/views/DailyRecommendationView.vue`, `GalleryView.vue`, `DailyImageDetailView.vue`):

- IntersectionObserver で実際にビューポートに入った画像を記録（スクロールで到達していないページ末尾を誤って「閲覧」扱いしない）
- バッチして `POST /impressions` に送信（デバウンス 2 秒 + `beforeunload`）

**API** (`worker/api.py`): `POST /impressions`（`require_admin` 必須、`/favorites/*` と同じ Firebase ID token）

**MongoDB 新コレクション `impressions`**:

```js
{
  _id: ObjectId,
  imageId: ObjectId,      // images._id
  sessionId: String,      // 1閲覧セッション
  view: "daily" | "gallery" | "archives" | "similar" | "detail",
  sortField: String,      // "inferences.eva02_pixiv_private_nnpu_joblib.score"
  date: "2026-08-04",     // 対象日
  page: Number,
  rank: Number,           // 日内の絶対順位（percentile 特徴の元）
  dwellMs: Number,        // ビューポート滞在時間
  openedDetail: Boolean,  // 詳細を開いた = 弱い正例シグナル
  viewedAt: Date,
}
```

インデックス: `{imageId: 1, viewedAt: -1}`, `{viewedAt: -1}`, `{sessionId: 1, rank: 1}`

**得られる追加シグナル**（お気に入りより粒度が細かい）:

- 詳細ページを開いた = 「気になったが登録しなかった」→ **中間ラベル**
- 滞在時間 = graded relevance（NDCG の grade に使える）
- `/gallery` での表示 = お気に入りの再確認（正例の強度）
- 類似画像からの遷移 = そのクエリ画像への強い興味

データ量: 1 日 200〜700 impression × 365 日 ≒ 年間 10〜25 万ドキュメント。無視できるサイズ。

### 3.2 【最優先】特徴量ストア

**現状の最大のボトルネック**: 特徴量は `pu-learning/data/features/*.h5` に **234,939 件しかなく**、MongoDB には残っていない。新モデルを作ったり過去画像を再スコアするたびに **1.16M 枚に GPU を回し直す**必要がある。これでは「継続的な更新」が成立しない。

**方針**: `worker/main.py` が推論時に既に計算している 3 つの特徴量を、その場で永続化する（追加 GPU コストはゼロ）。

サイズ試算（1.37M 枚）:

| 特徴 | 形式 | 1枚 | 全体 |
|---|---|---|---|
| eva02 (1024) | dense fp16 | 2 KB | **2.7 GB** |
| pixai (13,461) | sparse（閾値 0.01、~300 tags: int16 idx + fp16 val） | ~1.2 KB | **1.6 GB** |
| deepdanbooru (6,000) | sparse（閾値 0.01、~200 tags） | ~0.8 KB | **1.1 GB** |

`/mnt/cache2` の空き 1,020 GB に対して合計 **5.4 GB** ——全く問題ない。

**保存先の使い分け**:

| 特徴 | 保存先 | 理由 |
|---|---|---|
| eva02 (1024, dense) | **Qdrant `image_embeddings`**（既に 603,731 点） | ベクトル検索にも学習にも使える。scroll API で一括取得可能 |
| pixai / deepdanbooru (sparse) | **`/mnt/cache2/danbooru-ml-classifier/features/{YYYY-MM}/{shard}.parquet`** | 日付シャードで追記のみ。学習時に必要月だけ読む。Mongo を肥大化させない |

Mongo の `images` ドキュメントには `features: {stored: true, shard: "2026-08", eva02InQdrant: true}` のようなポインタだけを持たせる。

**バックフィル順序**（優先度順）:

1. **閲覧済み 22,804 件**（今回の学習に必須）— 数時間
2. お気に入り 1,783 件全部（date なしの Twitter 42 件含む）
3. 直近 90 日の全画像（評価・再スコア用）
4. 残り全体（バックグラウンドで段階的に）
5. **ディスク逼迫による古い画像削除の対象**（`worker/prune_old_images.py`、30日超・低ランク画像）— 本来は4に含まれる最低優先度の画像だが、ディスク容量問題（`/mnt/cache2` 88%使用）により早期にバックフィルしないとファイル削除で永久に特徴抽出できなくなる。`prune_old_images.py` は `features.stored=true` の画像しか削除しないため計画とは非衝突だが、現状カバレッジは30日超の画像の3.5%程度（4.7万/135万件、2026-09時点）しかなく、このままでは削除が進まない。最古の日付から`backfill_features.py --date-from/--date-to`で数日〜1週間規模の先行バックフィルスプリントを都度ユーザー確認のうえ実行し、優先度4の消化を前倒しする運用とする。以降は `worker/main.py` が毎日の GPU ウィンドウ内で `PRUNE_BACKFILL_BATCH_SIZE`(既定2000件/日)ずつ最古の未バックフィル画像を段階的に処理し続ける。

`backfill_qdrant.py` / `backfill_multiaxis_qdrant.py` が既に同型の処理をしているので、これを拡張するのが最短。

### 3.3 Qdrant の活用

Qdrant は現在「類似画像表示」にしか使っていないが、**推薦精度の改善に直接使える**。

| # | 用途 | 内容 | 学習要否 |
|---|---|---|---|
| Q1 | **kNN 嗜好スコア（最重要）** | 各候補画像について、お気に入り 1,783 件に対する top-k cosine 類似度の max / mean / count(>0.8) を特徴量にする。Qdrant への 1 クエリで得られる | **不要** |
| Q2 | **近重複による負例クリーニング** | 負例のうちお気に入りと cosine > 0.95 のものを除去（2.2 の R2） | 不要 |
| Q3 | **多様性リランキング (MMR)** | トップ 50 が同一作家・同一シリーズで埋まるのを防ぐ。`λ * score - (1-λ) * max_sim_to_selected` | 不要 |
| Q4 | **軸別嗜好モデル** | `image_embeddings_multiaxis` の `character` / `situation` / `style` それぞれで kNN スコアを取り、「キャラは好みだが構図が好みでない」を分離。将来のカテゴリ機能とも噛み合う | 不要 |
| Q5 | ラベル伝播 | お気に入りの近傍を疑似正例として学習データを水増し。**R3 のループを悪化させるので慎重に**、効果検証してから | 学習に影響 |

**Q1 は特に有望**: 現行モデルは「過去の pixiv ブックマーク全体」から学んだ静的な関数だが、kNN スコアは **最新のお気に入りが即座に反映される**（再学習不要でオンライン更新される推薦）。お気に入りを 1 つ追加した瞬間に翌日のランキングが変わる。

Qdrant のカバレッジは現在 603,731 / 1,157,848（52%）なので、3.2 のバックフィルと合わせて 100% にする必要がある。

### 3.4 その他 MongoDB の整備

- **`pending` が 6,177 件溜まっている**。当初「`main.py` は手動実行」と記載したが誤り——このマシンの GPU アプリはすべて `HakataMatrix-app-controller-claude`（常駐アプリ）が排他制御しており、`main.py`（cronjob app 扱い）は同コントローラが**毎日 05:00 JST に自動実行**し、実行前後で VRAM を確保・解放する。よって推論用の独立した systemd timer は不要（追加すると二重実行やVRAM競合を招く）。
- 新コレクション `modelRegistry`（4.2 参照）
- 新コレクション `trainingSnapshots`（学習に使ったラベルセットの再現性確保）

## 4. モデル改善プラン

### Phase A — 学習なしの即時改善（1〜2 日）

MongoDB にある値と Qdrant だけで完結。特徴量抽出もモデル学習も不要。

1. **アンサンブルスコア**: 日内 percentile rank の平均を2構成で `inferences` に書き込む（1.5.1参照、実装時は Virgo/Libra と命名）
   - `ensemble_virgo_v1`: private系9モデル（3特徴×3手法）平均 — 実測: p0-1 ページ内AUC 0.656（Gemini）→ **0.693**
   - `ensemble_libra_v1`: 上位5モデル平均 — p0-1では0.676だがp5-19以降で0.70台まで伸びる（深いページ向け）
   - どちらか一方に決め打ちせず、両方を named sort タブとして出し実運用で比較する（オフライン指標だけでは優劣が決まらないため、1.5.1参照）
2. **kNN 嗜好スコア（Q1）を混ぜる**: `0.7 * ensemble + 0.3 * knn_favorite_similarity`（次フェーズ）
3. **負例クリーニング（Q2）を評価に適用**
4. UI に「Virgo」「Libra」タブを追加し、Gemini と並べて実運用比較

**成果物**: `pu-learning/scripts/build_impressions.py`（1.2 の再構成 + 2.3 の重み付け）と `pu-learning/scripts/eval_impressions.py`（1.5 の評価表）。以降の全 Phase の評価基盤になる。

### Phase B — 教師あり re-ranker（1〜2 週）

**2 段構成にする**（1.16M 枚全部に重いモデルは回せないため）:

```
stage 1 (recall):    既存 PU モデル or アンサンブルで日内トップ 500 に絞る
stage 2 (precision): re-ranker で 500 枚を並べ替えて表示
```

**stage 2 の学習データ**: 25,850 impressions（正例 1,740）+ 2.3 の重み

**特徴量**（低次元・少データ向き。生の 13k 次元は使わない）:

| 群 | 次元 | 内容 |
|---|---|---|
| モデルスコア | ~36 | 既存 30 モデルの score/クラス確率。**日内 percentile に正規化**（日ごとのスコア分布差を吸収） |
| Qdrant kNN | ~12 | お気に入りへの max/mean/top10平均 cosine（eva02 + character/situation/style の 4 軸） |
| タグ | ~100 | `importantTagProbs` の deepdanbooru/pixai 各 50 |
| メタ | ~8 | type, 解像度, アスペクト比, 曜日, moderation rating, age estimation |

**モデル**: LightGBM (LambdaRank or binary + scale_pos_weight)。正例 1,740 に対して ~156 次元なら妥当。線形ロジスティック回帰もベースラインとして必ず併記する。

**評価**: **時系列 holdout**（直近 30 日を test、それ以前を train）。ランダム分割は嗜好ドリフトとページ相関でリークするため厳禁。

**主要指標**: **Recall@50** ——「その日のお気に入りのうち何%が 1 ページ目に入るか」。実運用上ほぼ唯一意味のある指標。副次的に Recall@100, NDCG@50, ページ内 AUC。

### Phase C — PU モデル自体の再学習（2〜4 週）

確定負例が手に入ったので、**PU Learning から PNU (Positive-Negative-Unlabeled) Learning に移行できる**。

1. **正例の拡張**: 既存 pixiv_private 37k + **DMC お気に入り 1,783**（分布が推論時と一致する貴重な正例）
2. **確定負例の導入**: nnPU の非負リスク補正の代わりに、観測済み負例を直接使う。`elkan_noto` の事前確率推定も観測負例で校正できる
3. **sankaku の特徴量抽出**（現在完全に学習対象外、閲覧画像の 23%）
4. **新ラベル `dmc_favorite`** を `POSITIVE_LABELS` に追加し、既存の 27 モデル生成パイプラインをそのまま流用

`train_pu.py` は `{feature}_{label}_{method}.joblib` 命名で `--labels` フラグを持つので、`dmc_favorite` ラベルを追加するだけで 9 モデル（3特徴 × 3手法）が既存コードで学習できる。`main.py` は `MODELS_DIR.glob("*.joblib")` なので、ファイルを置くだけで自動的に推論される。

### Phase D — 特徴表現の刷新（任意・長期）

- EVA02 encoder の LoRA ファインチューニング（正例 1,783 + 負例 24,110 は最小限だが、LoRA なら可能）
- SigLIP / CLIP 系の追加特徴（現在の 3 特徴はすべて Danbooru タグ空間か EVA02 で、意味的多様性が低い）

Phase A–C で頭打ちになってから着手すべき。

### 評価プロトコル（全 Phase 共通）

1. **時系列 holdout**: 直近 30 日 = test、それ以前 = train。日をまたいだリークなし
2. **主指標**: **ページ内AUC**（深度帯別: p0-1 / p0-4 / p5-19 / p20+）。**Recall@50 は主指標にしない**——1.5.2 で確認した通り、Gemini由来のラベルに対するRecall@50はGemini自身が構造的に有利になる自己言及的指標のため、参考値としてのみ記録し、常に「Geminiとの一致度」である旨を注記する
3. **既存 eval set も継続**: `data/metadata/eval_manifest.parquet` の 9,571 件（手動ラベル）。ただし閲覧済み集合と 469 件重複しているので、**学習データから除外**すること
4. **不偏データの確保**: 毎日 1 ページ目にランダム枠を 2〜3 枚混ぜる（ε-greedy）。R3 のフィードバックループを検出・補正する唯一の手段。年間 ~1,000 件の不偏サンプルが貯まる
5. **アブレーション必須項目**: 信頼度重み `w` の有無、負例クリーニングの有無、kNN 特徴の有無
6. **学習型モデルは stage-2（候補絞り込み後の再ランク）としてのみ評価する**（1.5.3参照）。全画像への直接適用はテスト対象に含めない

## 5. 継続的モデル更新の仕組み

### 5.1 ループ全体像

```
日次 15:00 JST  danbooru-fetch.timer     ランキング取得 + 画像DL          （既存）
日次 16:00 JST  danbooru-infer.timer     main.py: 推論 + 特徴量永続化      （新規）
                                          + Qdrant upsert
随時            ユーザー閲覧              → impressions / favorites 記録    （新規）
週次 日曜       danbooru-retrain.timer   re-ranker 再学習 → 評価ゲート     （新規）
                                          → 合格なら models/ に配置
月次            （手動起動）              PU モデル full 再学習             （新規）
```

### 5.2 モデルレジストリ

`data/models/registry.json` + MongoDB `modelRegistry` コレクション:

```js
{
  _id: "reranker_v3",
  createdAt: ISODate,
  trainedOn: {impressionsUntil: "2026-08-01", nPos: 1740, nNeg: 24110},
  featureSpec: ["model_scores_v1", "qdrant_knn_v1", "tags_v1"],
  metrics: {recall_at_50: 0.61, ndcg_at_50: 0.44, page_auc: 0.72},
  baseline: {model: "reranker_v2", recall_at_50: 0.58},
  status: "promoted",   // candidate | promoted | rolled_back
  mongoKey: "reranker_v3_joblib",
}
```

### 5.3 昇格ゲート（自動）

再学習後、**直近 30 日の impressions**（学習に使っていない期間）で評価し:

- `recall@50` が現行昇格モデルを **下回ったら昇格しない**（candidate のまま保存）
- 上回ったら `promoted` にし、`data/models/` に配置 → `main.py` の glob が自動的に拾う

ロールバックは `registry.json` の `promoted` を書き戻すだけ。

### 5.4 UI 側のバージョン非依存化

`public/src/config/namedSorts.ts` はモデルキーをハードコードしているため、モデルを更新するたびにフロントエンドの修正・デプロイが必要になる。

**対策**: `GET /inference-models` に「エイリアス」の概念を追加し、`recommended` → `inferences.reranker_v3.score` のマッピングをサーバ側で解決する。UI には「Recommended」という固定タブを置き、中身のモデルはサーバ側で差し替えられるようにする。既存の星座タブは実験・比較用として残す。

### 5.5 新モデル追加時の過去画像スコアリング

新モデルを追加しても、過去画像には `inferences.<new_model>` が存在しないため、過去日付を見返すとランキングが壊れる（`_get_sorted_ids` は `{$exists: True}` でフィルタしている）。

3.2 の特徴量ストアがあれば、**GPU 不要で CPU バッチ再スコアが可能**になる。これが特徴量ストアを最優先に置く理由。

- 全 1.16M 枚 × 線形モデル → 数分
- LightGBM re-ranker → 数十分

再スコア範囲は「直近 180 日」に限定してもよい（それ以前は実質見返さない）。

### 5.6 運用上の注意

- **再構成インプレッションは日々変化する**: `status: pending → inferred` の遷移や新規モデル追加で日内ランキングが変わるため、Phase A/B のラベルは**スナップショットとして `trainingSnapshots` に保存**し、再現性を確保する
- **ラベルの陳腐化**: 3.1 の実測ログが十分（半年程度）貯まったら、1.2 の再構成ラベルは学習から段階的に外し、重みを下げる
